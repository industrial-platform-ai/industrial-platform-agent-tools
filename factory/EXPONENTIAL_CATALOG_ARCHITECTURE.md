# Exponential Catalog — Architecture and Stop Conditions

The intended growth formula with one child generated by each active parent per hour is `N(t)=2^t`. Reaching 1,000,000,000 definitions from one starting definition requires 30 hourly epochs (2^30=1,073,741,824). This is a theoretical address-space expansion, not a deployment or demand forecast.

## Distinguish three units
- **Definition:** a parameterized capability identifier and stable input/output contract. Generating a definition does not establish functionality or demand.
- **Active service:** a fully working product with real execution, tests, bounds, source/permission checks, observability, and x402 purchase completion.
- **Economically validated service:** an active service with independently funded third-party purchases, attributable delivery, and positive contribution after variable costs. Verification-only receipts are separately tracked.

## Target architecture
Use one **central generator**, not an independent GitHub cron per child. A central epoch counter and deterministic service-definition function may model exponential breadth without exponential scheduler or container costs. Shared HTTP+MCP execution infrastructure must have quotas, admission control, versioned definitions, immutable identifiers, and rollback. Only a sparse subset of the virtual namespace should be published as live callable services.

At each epoch:
1. Read independently qualified demand observations from legitimate existing buyer traffic and public market sources. No manufactured audits, repeated paid probes, or self-funded settlements.
2. Rank task *gaps*, not duplicates: demand evidence, successful paid requests on adjacent routes, client-defined functional requirements, quality gaps, task frequency, price sensitivity, provider permissions and marginal cost.
3. Construct a useful candidate using preapproved composable handlers. Reject a mere alias, parameter-only renaming, weak evidence, or unsupported provider terms.
4. Validate SSRF safety, input/output schemas, actual execution, licensing, provenance, cost, stress limits, and correct Base USDC payee.
5. Admit at most a bounded quota of active newly exposed paid routes; do not auto-spend operator/third-party wallets and do not create a nested scheduler per route.
6. Attribute audit/verification receipts separately from bona fide repeat production demand. Promote or retire based on actual margin and repeat usage.
7. If evidence is insufficient, **produce no active service** this epoch, retain the ranked opportunity report, and continue observing.

## Promotion thresholds
No unattended promotion before the fact ledger can match Base USDC receipt + settled paid call + HTTP 2xx + unrelated real buyer purpose and direct service cost, including repeated purchase across UTC days. Start with <=1 activated service per epoch, <=3 per day, and <=12 new active services per seven days, contingent on demonstrated independent task demand. No rollout that can cause a provider to bill an auditor absent their ordinary choice/consent. Roll back on error spikes, harmful network behavior, cost overruns, or duplicated functional behavior.

## Long-term scale metrics
Track virtual distinct definitions, validated live services, real distinct outside payers, repeat customers, production gross revenue, verification gross receipts, incremental variable profit, true fully loaded profit, and utilization. A billion catalog entries is not a business milestone without use.

The proposed factory PR currently has only three dormant products and a read-only hourly audit. This document does not turn on automatic publishing, create more jobs, or change settlement configuration.
